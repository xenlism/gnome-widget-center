# Handover — 2026-08-09 session (Border/Opacity fields, Force UX trap, blur pilot migration)

Three user-reported bugs this session, from a real desktop test (screenshot),
not a hypothetical report:

1. Blur blurs the whole widget, not just the background.
2. Border / Opacity "don't work."
3. Overlay sort/search overflows a card's width — **not yet investigated,
   need a screenshot of the actual overlay screen this refers to** (the
   supplied screenshot showed the live desktop with widgets placed, not
   the Widget Center picker overlay — nothing in `widgetCenterOverlay.js`'s
   sort/search layout looked obviously overflowing on inspection, but that
   was a static read, not a runtime one against the specific screen the
   user meant). Flagging as open, not fixed.

## Root causes found, in order of investigation

### A. 22 widgets had NO Border/Opacity fields in their own config.json at all

Grepped every `widgets/*/config.json` for `borderEnabled` — **zero** hits,
project-wide. The engine (`lib/widgetVisualKit.js`'s `borderCss()` /
`applyCardOpacity()`) was already fully correct and already Force-aware
(confirmed against `HANDOVER_FORCE_SETTINGS.md` Addendum 9's fixes, still
in place) — but with no widget exposing `borderEnabled`/`borderColor`/
`borderWidth`/`opacity` in its own Appearance settings, and no
`getDefaultSettings()` spreading `BORDER_DEFAULTS`/`OPACITY_DEFAULTS`
either, there was simply no way for a user to turn border/opacity on
**per-widget** — only the global Force switches could reach it at all.

Fixed for the 22 widgets that call `widgetVisualKit.js`'s `cardStyleCss()`
directly (the same ~24-widget group `HANDOVER_FORCE_SETTINGS.md`'s
Addendum 4/9 already named as the blur-affected set — `calendar-modern`,
all `circles-*`, all `media-player-*`, `power-menu-bar`,
`settings-control-bar`, `switches`):

- `config.json`: new "Border & Opacity" group inserted right after each
  widget's main color/appearance group (always `tabs[0].groups[0]` —
  verified true for all 22 before doing this programmatically). 4 fields:
  `borderEnabled` (switch), `borderColor` (colorpicker, `visibleIf:
  borderEnabled`), `borderWidth` (spinbutton, `visibleIf: borderEnabled`),
  `opacity` (slider 0–100%, always visible, no enable gate — matches
  `OPACITY_DEFAULTS`'s own always-on shape).
- `widget.js`: added `BORDER_DEFAULTS, OPACITY_DEFAULTS` to each file's
  existing `widgetVisualKit.js` import, and `...BORDER_DEFAULTS,
  ...OPACITY_DEFAULTS,` right after each file's existing
  `...SHADOW_DEFAULTS,` spread in `getDefaultSettings()`.
- No widget.js render-path changes needed beyond the above for 21 of the
  22 — `cardStyleCss()` already includes border by default
  (`includeBorder: true`), and opacity is applied centrally by
  `extension.js`'s `_applyCardEffects()` (Addendum 9), so both "just
  start working" once the settings exist. `circles-battery` is the
  exception — see §C below, migrated further this same pass.
- `calendar-modern` needed no special-casing despite using `cardColor`
  instead of `backgroundColor` for its own background field — the new
  group was still inserted after its `colors` group correctly, and its
  border/opacity are unrelated to that naming.
- **Not done**: the other ~33 widgets that build their CSS by hand
  (`weather-modern`, the `geek-*` family, `clock-modern`, launcher
  widgets, monitor widgets, etc. — anything NOT importing `cardStyleCss`
  from `widgetVisualKit.js`) still have no Border/Opacity fields. Adding
  them means hand-editing each one's own `set_style()` string to append
  `borderCss(this._settings)`, not just a defaults/config.json change —
  didn't want to make 33 blind, untested edits to hand-rolled CSS strings
  in one pass. Left for a follow-up, listed file-by-file at the bottom.

### B. Force Border/Opacity: real UX trap, not a mechanism bug

`lib/prefsPageBuilders.js`'s Border group has **two independent
switches** — "Enabled" and "Force this border on every widget" — and
`borderCss()` checks `forced.enabled` before it even looks at whether
Force is on. Turning ONLY "Force" on (the switch whose label sounds like
it should be sufficient on its own) produced **zero** visible change,
which is exactly what a user testing "does Force Border work" would hit
first. Confirmed this is what the user actually tested against (asked
directly, they said Force Settings, not per-widget).

Fixed in `lib/prefsPageBuilders.js`:
- `borderForceRow`'s `notify::active` handler now auto-flips
  `borderEnabledRow.active = true` when Force is turned on while Enabled
  is still off (one-directional — turning Enabled back off later still
  works normally, even with Force staying on).
- Group description corrected — it previously claimed Border "applies to
  any widget that opts in via metadata.json's themeable: true", which was
  stale/wrong: `borderCss()` is consulted by `cardStyleCss()` for every
  non-themeable widget too (that's the whole engine §A above relies on).
  Rewritten to actually explain the Enabled/Force interaction instead.
- Opacity has no separate Enabled gate (by design — `opacityValue()` just
  reads `forced.value` directly), but the equivalent trap exists there:
  turning Force on with the value left at its 100% default is
  indistinguishable from doing nothing, since 100% opacity IS "no
  visible fade." Added a subtitle on the opacity spin row spelling this
  out rather than changing behavior — 100% remains a legitimate value to
  force, just not a very demonstrative one for someone testing the
  toggle.

### C. Blur — pilot migration done for ONE widget (`circles-battery`), rest still open

Per `HANDOVER_FORCE_SETTINGS.md` Addendum 9's own "Known limitation,
flagged not fixed": `applyCardBlur()` was being called on `entry.actor`
centrally (`extension.js`'s `_applyCardEffects()`), which for every
widget except (previously) zero of them is the SAME actor the widget's
own labels/icons/drawing areas are children of — so blur caught
everything, not just the background fill. `createLayeredCard()`/
`applyLayeredCardStyle()` (`lib/cardLayers.js`) already existed to solve
exactly this, just had no callers anywhere in the tree.

Migrated `widgets/circles-battery/widget.js` as a concrete, working
reference:
- `buildActor()`: replaced the single `St.Bin` root with
  `createLayeredCard({contentStyleClass: 'circles-battery-root'})` —
  `this._actor = layers.root`, ring/label content now added to
  `layers.content` instead of directly to the old root.
- `_render()`: replaced `this._actor.set_style(cardStyleCss(...))` with
  `applyLayeredCardStyle(this._layers, this._settings, {...})` — applies
  background-color/border/corner-radius/shadow CSS AND blur AND opacity
  to `layers.background` only, never touching the ring/label content.
- **`extension.js`'s `_applyCardEffects()` updated to detect this**: if
  `entry.instance._layers` exists (the new convention any migrated
  widget's `buildActor()` sets), the method now returns immediately
  without touching `entry.actor` at all. This was a real bug I'd have
  introduced otherwise — `entry.actor` for a layered widget IS
  `layers.root`, the parent of BOTH background and content, so blurring/
  fading it centrally would still blur/fade everything, silently
  undoing the entire point of the background/content split. Caught this
  before shipping the pilot, not after.
- Border/Opacity fields for `circles-battery` (from §A) work exactly the
  same as before this migration — `applyLayeredCardStyle()` still reads
  the same `settings.borderEnabled`/`opacity` fields, just applies them
  to `layers.background` now instead of the old single root.

**Not done**: the other 21 widgets in the `cardStyleCss()` group (see §A's
list) still blur their entire card, not just the background — same
limitation as before, just no longer true for `circles-battery`. Each one
needs the same three-part treatment `circles-battery` got above:
`createLayeredCard()` in `buildActor()`, moving existing children onto
`.content` instead of the old root, and swapping the `_render()` call
from `cardStyleCss()`+`set_style()` to `applyLayeredCardStyle()`. The
`extension.js` `_applyCardEffects()` detection fix already covers all of
them automatically once each one sets `this._layers` — no further
`extension.js` changes needed as more widgets get migrated.

## Addendum 2 (handover v4, same day) — Shell crash, sortbar width, Force border/opacity root cause

Three more user reports, from a live `journalctl --user -f -o cat /usr/bin/gjs`
capture (Shell actually crashed - "Lost connection to Wayland compositor").

### D. Pango markup crash — FIXED, and NOT limited to the battery widgets

`journalctl` showed `Failed to set text '...Border & Opacity' from markup` and
`'...Low battery color (< 20%)' from markup`. Root cause: `Adw.ActionRow`/
`ExpanderRow`/`EntryRow`/`PasswordEntryRow`/`SpinRow`/`SwitchRow`/`ComboRow`
`title`/`subtitle` are parsed as **Pango markup** by libadwaita, and this
codebase was handing every one of them a widget's own `config.json`
`label`/`description` **raw** - any author text containing `&` or `<`
(not just these two strings) throws a markup parse error, which is what
took the whole Shell process down. This affects **every widget with a
config.json field/group whose label or description contains `&` or `<`**,
not just `circles-battery`/`circles-battery-half` - the "Border & Opacity"
group alone (added project-wide last session, §A) put the literal string
"Border & Opacity" into 22 widgets' Preferences pages.

Fixed at the three render points that turn `field`/`group`/`tab` labels
into Adw markup titles - `GLib.markup_escape_text()` added right at each
call site, NOT on the shared `field.label`/`field.description` strings
themselves (those are still used raw for `tooltip_text()` and plain
`Gtk.Label` headers elsewhere, which do NOT parse markup - escaping there
too would have shown literal `&amp;` instead of `&`):
- `lib/widgetConfigUI.js` - `tabLabel`/`groupLabel`/`groupDescription`
  (the `Adw.PreferencesGroup` title/description built from a widget's own
  `config.json` tab/group labels).
- `lib/widgetConfigFieldRows.js` - every `title:`/`subtitle:` in every
  `_xRow()` field-builder, via a new local `_esc()` helper.
- `lib/settingsSchemaUI.js` - same `_esc()` treatment, for widgets that
  define their own custom `settingsSchema.json` fields (General tab).

### E. Overlay sort/search bar width — now matches the card grid exactly

User: the bar's width should equal the card display area's width, not
stretch edge-to-edge. `_buildGrid()`'s card grid is centered at a fixed
`columns * 480 + (columns-1) * 16` px (see `_gridColumns()`'s own doc
comment for those numbers), but `_buildSortBar()` was `x_expand: true`
with its own `8px 24px` CSS padding - edge-to-edge across the whole
overlay, unrelated to the grid's actual (narrower, centered) width on any
monitor with room for 3 columns.

Fixed: new `_gridContentWidth()` helper computes the same
`columns*480+(columns-1)*16` figure; `_buildSortBar()` now sets that as
the bar's own fixed `width`, `x_expand: false`, `x_align: CENTER` -
sitting centered at exactly the grid's own width, same as the grid
itself. `.wc-overlay-sortbar`'s CSS padding dropped from `8px 24px` to
`8px 0` (horizontal padding would otherwise widen the bar past the
now-exact `width`).

### F. Force border/opacity had no effect — ROOT CAUSE FOUND AND FIXED

Real bug, not a UX trap this time. `lib/themeService.js`'s
`setGlobalTheme(patch)` - the method `lib/prefsPageBuilders.js`'s
`saveBorder()`/`saveOpacity()` both call - only ever merged/persisted
`patch.background`, `patch.cornerRadius`, and `patch.dropShadow` into
`theme.json`. `patch.border` and `patch.opacity` were silently dropped on
every call, despite `getGlobalTheme()` (the read side, right above it)
always having read `border`/`opacity` back out and despite
`widgetVisualKit.js`'s `borderCss()`/`opacityValue()` already being fully
Force-aware. The whole chain downstream of the save (file-watch →
`setForcedTheme()` → `_reapplyTheme()`) was correct and unchanged - the
edit itself just never reached disk, so there was nothing new for that
chain to pick up. This means Force Border/Opacity has likely never worked
since the day those two groups were added, independent of anything from
last session.

Fixed: `setGlobalTheme()` now merges/persists `border` and `opacity` the
same way it already did `background`/`cornerRadius`/`dropShadow`.

Validated: `node --check` clean on `lib/themeService.js`,
`lib/widgetConfigUI.js`, `lib/widgetConfigFieldRows.js`,
`lib/settingsSchemaUI.js`, `lib/widgetCenterOverlay.js`. **Not**
runtime-tested against real GNOME Shell — please re-check the exact
crash scenario (open Preferences → a `circles-battery*` widget's Border &
Opacity group) and the Force Border/Opacity toggle live; these were
static fixes against a real crash log and a read of the save/load
asymmetry, not confirmed against a running Shell.

## Addendum 4 (handover v6, same day) — no more markup crash; 3 new fixes

Good news first: user re-tested with a clean (non-scrollback) journalctl
capture after enabling the extension fresh and the markup crash did
**not** reproduce - v5's escaping fix holds. Three new items from that
session, all fixed:

### G. `circles-battery-half` ring still overflowing past the card

Root cause was the `set_translation()` call in `_layoutChildren()` (not
the missing `clip_to_allocation` from v3/v4, which IS in place and
loaded - the earlier per-widget-folder-only dev-watcher-caching theory
didn't pan out under closer look at the actual math). That translation
shifted the ring's DrawingArea outward by `CARD_PADDING` (14px) on top of
a row layout that already placed the ring flush with the padded content
edge - net effect, the ring's own curve/stroke painted `CARD_PADDING` px
past the card's actual edge.

Fixed by dropping the translation entirely - the ring column now just
respects the same padding every other element in the card already does.
Trades a few px of "hugs the border exactly" snugness for the ring never
being able to escape the card, full stop. Also added
`clip_to_allocation: true` directly on `this._ringArea` itself (belt and
suspenders, independent of `createLayeredCard()`'s own content-layer
clip from v3).

### H. Escape didn't close the widget-center-prefs-app.js window

`Adw.PreferencesWindow`'s built-in Escape handling only pops a
subpage/search back to the top level - it doesn't close the window
itself. Added a bubble-phase `Gtk.EventControllerKey` on the window that
closes it on Escape; bubble phase (not capture) so it never steals
Escape from something closer to the focus that wants to handle it first
(a search entry, a subpage, an open color-picker popover, etc.) - this
only fires once nothing nearer has already consumed the key press.

### I. Clicking "Preferences" in the overlay now closes the overlay

Previously `_openExtensionPreferences()`/`_openWidgetSettings()` (both go
through `_launchExternalPrefsWindow()`) HID the overlay while the spawned
prefs window was open and re-`show()`-ed it once that window closed again
- deliberate at the time, to work around the spawned window rendering
behind the overlay's Shell-chrome layering (see
`_launchExternalPrefsWindow()`'s own long doc comment, unchanged). Per
user ask, that now calls `this.close()` instead of `hide()` - the overlay
is gone for good, not brought back once Preferences closes.
`_watchForExternalPrefsWindow()` still runs afterwards for its
`make_above()`/`activate()` half (still needed for the same
chrome-layering reason), it just has nothing left to re-`show()`.

Validated: `node --check` clean on
`widgets/circles-battery-half/widget.js`, `widget-center-prefs-app.js`,
`lib/widgetCenterOverlay.js`. Still not runtime-tested against real GNOME
Shell.

## Addendum 8 (handover v10, same day) — §A: calendar-header done; clock/calendar-minimal/mini-notes/system-stats/qa-test-widget investigated and left open on purpose

### `calendar-header` — done, different treatment than any prior batch

Unlike every widget closed so far, `calendar-header`'s card has no single
flat background at all — it's visually split into two independently-
colored pieces, `this._header` (top, `headerColor`, rounded top corners
only) and `this._body` (bottom, `bodyColor`, rounded bottom corners
only), with `this._actor` itself carrying only `border-radius: 22px` +
shadow and no fill of its own. `cardStyleCss()` assumes one flat
background, so a straight swap would have been wrong here (it would
overwrite the split-color design with a single flat fill). Instead:
- Added `_borderCss(this._settings)` (imported as `borderCss` from
  `widgetVisualKit.js`, same as `power-menu`/`settings-control` got in
  v9) to `this._actor`'s existing style string — draws a border wrapping
  the OUTSIDE of both header+body pieces together, at the actor's
  existing 22px radius, without touching either sub-piece's own fill
  color.
- Opacity needed no widget.js change, same reasoning as v9's Group 3 —
  `extension.js`'s `_applyCardEffects()` already applies it centrally to
  every non-layered widget's root actor.
- `...BORDER_DEFAULTS, ...OPACITY_DEFAULTS` added to
  `getDefaultSettings()`; `borderOpacity` config.json group inserted
  after the widget's `colors` group, with its own `description`
  overridden (rather than left blank like every other batch) to say
  "Border wraps the whole card (header + body); opacity fades the entire
  widget" — the default blank description would have been misleading
  here specifically, since a user could reasonably expect the border to
  follow the two-tone split rather than wrap it as one shape.

### `clock` and `calendar-minimal` — investigated, deliberately left open

Both have **no card background at all today** — not a hand-rolled
variant of the same concept every other §A widget had, but genuinely

day number... deliberately no full date, no day-of-year..."*. Confirmed
neither `.clock-widget-root` nor `.calendar-minimal-widget-root` has a
stylesheet.css rule supplying a background either (grepped, no hits —
and both widgets' own comments already note this host doesn't load
per-widget stylesheet.css into the Shell theme context yet anyway).

Also found, while reading `calendar-minimal`: its `getDefaultSettings()`
already has a `cardColor: '#ffffff'` default that is **never read
anywhere in `_render()`** and **never exposed in `config.json`** — a
dead setting, not a partially-wired one. Flagging rather than fixing,
since it's ambiguous whether this is leftover cruft from before the
"no chrome" design was finalized (safe to delete) or an early stub for a
future optional-background feature (safe to wire up) — either read is a
real content decision, not a mechanical one, and this session's batch
methodology deliberately doesn't make those blind.

introduce an actual card background/fill where explicitly none exists by

### `mini-notes` / `system-stats` — investigated, mechanism-blocked

prefs.js → settings.js → metadata.json's flat `settings` array), both

first giving each one an actual `config.json` (migrating off the
flat-array fallback entirely) — a bigger, per-widget migration, not a

"Appearance" group automatically to any settings page, but only for

radius via the older separate `theme.json` `ThemeService` per-widget
mechanism, not Border/Opacity via `cardStyleCss()`/`config.json` at all

Left both open.
